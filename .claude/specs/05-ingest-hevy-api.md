# Spec: Hevy API Ingestion

## 1. Overview

Implement automated ingestion of workout data from the Hevy REST API into the
FitMon raw schema. This spec covers:

1. A client layer (`src/ingestion/hevy_api_client.py`) — auth, requests, pagination, retries
2. An ingestion script (`src/ingestion/ingest_hevy_api.py`) — unpacking, transforming, upserting
3. Schema amendments to `raw.workout_sessions` — adding `hevy_workout_id` as conflict key
4. Schema amendments to `meta.ingestion_log` — adding `ingestion_type` and `failure_code`
5. A new CLI command `sync-hevy` wired into `src/cli.py`
6. A connection test
7. A cron setup guide

This spec does not cover Apple Health ingestion, dbt models, or Grafana dashboards.

## 4. Schema amendments

### A. `raw.workout_sessions` — add `hevy_workout_id`

The existing `workout_session_id` (UUID, PK) was generated by the DB for CSV
ingestion. The API provides Hevy's own native UUID per workout. A dedicated
column is required so both CSV and API paths use the same conflict key, preventing
duplicate rows for the same workout ingested via different transports.

**Add this column:**

| Column | Type | Constraints |
|---|---|---|
| `hevy_workout_id` | TEXT | Unique, not null for API-ingested rows |

**Conflict key for API upserts:** `hevy_workout_id`

SQL migration (add to `utils/create_raw_tables.sql` and run once):

```sql
ALTER TABLE raw.workout_sessions
ADD COLUMN IF NOT EXISTS hevy_workout_id TEXT UNIQUE;

ALTER TABLE raw.workout_sessions
ADD COLUMN IF NOT EXISTS deleted_at TIMESTAMPTZ;
```

### B. `raw.workout_sessions` — add API-sourced columns

The Hevy API payload contains fields not present in the CSV path. Store them
all — raw layer must be an exact copy of source data.

| Column | Type | Constraints | Source field |
|---|---|---|---|
| `hevy_workout_id` | TEXT | Unique | `workout.id` |
| `title` | TEXT | Nullable | `workout.title` |
| `description` | TEXT | Nullable | `workout.description` |
| `routine_id` | TEXT | Nullable | `workout.routine_id` |
| `hevy_updated_at` | TIMESTAMPTZ | Nullable | `workout.updated_at` |
| `hevy_created_at` | TIMESTAMPTZ | Nullable | `workout.created_at` |
| `deleted_at` | TIMESTAMPTZ | Nullable | `event["deleted_at"]` — NULL until soft delete is implemented |

### C. `raw.exercises` — add `exercise_template_id`

The API provides a stable `exercise_template_id` per exercise type. This is
the correct conflict key — not `exercise_name`, which can change.

| Column | Type | Constraints | Source field |
|---|---|---|---|
| `exercise_template_id` | TEXT | Unique | `exercise.exercise_template_id` |
| `supersets_id` | INTEGER | Nullable | `exercise.supersets_id` |
| `exercise_index` | INTEGER | Nullable | `exercise.index` |

### D. `raw.sets` — add API-sourced columns

| Column | Type | Constraints | Source field |
|---|---|---|---|
| `set_index` | INTEGER | Nullable | `set.index` |
| `distance_meters` | NUMERIC(8,2) | Nullable | `set.distance_meters` |
| `duration_seconds` | INTEGER | Nullable | `set.duration_seconds` |
| `custom_metric` | NUMERIC(8,2) | Nullable | `set.custom_metric` |

### E. `meta.ingestion_log` — two new columns

| Column | Type | Constraints | Purpose |
|---|---|---|---|
| `ingestion_type` | TEXT | Nullable | `'csv'` or `'api'` |
| `failure_code` | TEXT | Nullable | HTTP status code e.g. `'429'`, `'500'` |

## 7. `src/ingestion/hevy_api_client.py`

This file handles all HTTP concerns. The ingestion script never calls `requests`
directly — it only calls functions from this module.

### Constants

```python
BASE_URL = "https://api.hevyapp.com/v1"
PAGE_SIZE = 10          # always use max
REQUEST_DELAY = 1.0     # seconds between paginated requests
MAX_RETRIES = 3
RETRY_BACKOFF_BASE = 2  # seconds; retry waits 2^attempt seconds
```

### Functions to implement

**`get_headers() -> dict`**
Returns auth header dict:
```python
{"api-key": settings.HEVY_API_KEY}
```

**`make_request(url: str, params: dict) -> dict`**
- Makes a single GET request with auth headers and timeout (10 seconds)
- On non-200 response: retries up to `MAX_RETRIES` times with exponential backoff
- Logs each retry attempt with status code
- On 401: raises immediately with a clear error — no retry (bad API key won't fix itself)
- On 429: waits `Retry-After` header value if present, else uses backoff
- After max retries exhausted: raises `RuntimeError` with status code — caller logs to `meta.ingestion_log`
- Returns parsed JSON dict on success

**`fetch_workouts_page(page: int) -> dict`**
- Calls `GET /v1/workouts?page=<page>&pageSize=10`
- Returns full response dict including `page`, `page_count`, `workouts`

**`fetch_workout_events_page(since: str, page: int) -> dict`**
- Calls `GET /v1/workouts/events?since=<since>&page=<page>&pageSize=10`
- `since` is an ISO 8601 timestamp string
- Returns full response dict including `page`, `page_count`, `events`

**`verify_connection() -> bool`**
- Calls `GET /v1/user/info`
- Returns `True` if 200, raises on any other status
- Used by the CLI connection test command

## 8. `src/ingestion/ingest_hevy_api.py`

This file handles unpacking, transformation, and upsert coordination.
It never imports `requests` — only `hevy_api_client` and `src/db/postgres.py`.

### Sync mode logic

```
def get_last_sync_timestamp() -> str | None:
    Query meta.ingestion_log for most recent finished_at
    WHERE source = 'hevy_api' AND status = 'success'
    ORDER BY finished_at DESC LIMIT 1
    Returns ISO timestamp string or None if no prior run exists
```

If `None` → full sync via `GET /v1/workouts`
If timestamp exists → incremental sync via `GET /v1/workouts/events?since=<timestamp>`

### Unpacking the payload

**Full sync** — response shape:
```
workouts[]
  └── exercises[]
        └── sets[]
```

**Incremental sync** — response shape:
```
events[]
  └── type: "updated" → contains workout{} → same structure as full sync
  └── type: "deleted" → contains id + deleted_at → log and skip (TODO: soft delete)
```

Parser must branch on `event["type"]` before unpacking. Never assume all
events contain a `workout` key.

### Three unpacking functions

**`parse_session(workout: dict) -> dict`**
Maps workout-level fields to `raw.workout_sessions` column names:

| API field | Column |
|---|---|
| `workout["id"]` | `hevy_workout_id` |
| `workout["title"]` | `title` |
| `workout["description"]` | `description` |
| `workout["routine_id"]` | `routine_id` |
| `workout["start_time"]` | `started_at` |
| `workout["end_time"]` | `ended_at` |
| `workout["updated_at"]` | `hevy_updated_at` |
| `workout["created_at"]` | `hevy_created_at` |

**`parse_exercise(exercise: dict, hevy_workout_id: str) -> dict`**
Maps exercise-level fields to `raw.exercises` column names:

| API field | Column |
|---|---|
| `exercise["exercise_template_id"]` | `exercise_template_id` |
| `exercise["title"]` | `exercise_name` |
| `exercise["index"]` | `exercise_index` |
| `exercise["supersets_id"]` | `supersets_id` |
| `exercise["notes"]` | `notes` |
| `'hevy'` (hardcoded) | `source` |

**`parse_set(set_: dict, exercise_template_id: str, hevy_workout_id: str) -> dict`**
Maps set-level fields to `raw.sets` column names:

| API field | Column |
|---|---|
| `set_["index"]` | `set_index` |
| `set_["type"]` | `set_type` |
| `set_["weight_kg"]` | `weight_kg` |
| `set_["reps"]` | `reps` |
| `set_["rpe"]` | `rpe` |
| `set_["distance_meters"]` | `distance_meters` |
| `set_["duration_seconds"]` | `duration_seconds` |
| `set_["custom_metric"]` | `custom_metric` |

All nullable fields must default to `None` if key is missing — use `set_.get("field")`.

### Main ingestion loop

```
def run_sync(mode: str):
    log_run_start() → write to meta.ingestion_log (status='running')

    try:
        last_sync = get_last_sync_timestamp()

        if mode == 'full' or last_sync is None:
            pages = fetch all via GET /v1/workouts (paginated)
        else:
            pages = fetch all via GET /v1/workouts/events?since=last_sync (paginated)

        for each page:
            for each workout (or event):
                if event type == 'deleted':
                    log deletion, skip
                    continue

                session_row = parse_session(workout)
                upsert into raw.workout_sessions ON CONFLICT (hevy_workout_id)

                for each exercise in workout:
                    exercise_row = parse_exercise(exercise, hevy_workout_id)
                    upsert into raw.exercises ON CONFLICT (exercise_template_id)

                    for each set in exercise:
                        set_row = parse_set(set_, exercise_template_id, hevy_workout_id)
                        upsert into raw.sets

            time.sleep(REQUEST_DELAY)  ← after each page, before next request

        log_run_success() → update meta.ingestion_log (status='success', finished_at=now)

    except Exception as e:
        log_run_failure(error=e) → update meta.ingestion_log (status='failed', failure_code, error_message)
        raise
```

### Upsert SQL patterns

**`raw.workout_sessions`:**
```sql
INSERT INTO raw.workout_sessions (hevy_workout_id, title, description, ...)
VALUES (%s, %s, %s, ...)
ON CONFLICT (hevy_workout_id) DO UPDATE SET
    title = EXCLUDED.title,
    description = EXCLUDED.description,
    hevy_updated_at = EXCLUDED.hevy_updated_at,
    ...
```

**`raw.exercises`:**
```sql
INSERT INTO raw.exercises (exercise_template_id, exercise_name, source, ...)
VALUES (%s, %s, %s, ...)
ON CONFLICT (exercise_template_id) DO UPDATE SET
    exercise_name = EXCLUDED.exercise_name,
    ...
```

**`raw.sets`:** No stable single conflict key from the API — use composite
of `(hevy_workout_id, exercise_template_id, set_index)` as conflict key.
Add a unique constraint on this composite in the schema amendment.

## 11. Error handling rules

| HTTP code | Action |
|---|---|
| 200 | Parse and process response |
| 401 | Raise immediately — log "invalid API key", no retry |
| 429 | Wait `Retry-After` seconds (or backoff), retry up to MAX_RETRIES |
| 500 | Exponential backoff, retry up to MAX_RETRIES |
| Other 4xx | Log and raise — likely a bug in request construction |

All non-recoverable failures must write `status='failed'` to `meta.ingestion_log`
before raising. The script must never silently swallow exceptions.

## 15. Rules for implementation

- `hevy_api_client.py` is the only file that imports `requests`
- `ingest_hevy_api.py` never calls `requests` directly
- All DB logic stays in `src/db/postgres.py` — no SQL in ingestion scripts
- All SQL parameterized — never f-strings
- Raw layer stores exact API values — no cleaning, no type casting
- `ON CONFLICT DO UPDATE` on every upsert — never blind insert
- `HEVY_API_KEY` loaded from `.env` via `settings.py` — never hardcoded
- `time.sleep(REQUEST_DELAY)` after every paginated request — no exceptions
- Deleted events: log and skip — do not delete rows from raw tables

## 16. One-time backfill — CSV rows missing `hevy_workout_id`
 
### Why this is needed
 
CSV ingestion populated `raw.workout_sessions` using UUIDv5 as the primary key
and left `hevy_workout_id` as NULL. When a full API sync runs for the first time,
Hevy returns those same workouts with their native IDs. Because `hevy_workout_id`
is NULL on existing rows, the conflict key finds no match and inserts duplicate
rows for every workout already ingested via CSV.
 
The backfill script resolves this by matching CSV rows to API workouts on
`started_at` timestamp and populating `hevy_workout_id` on the existing rows
before the first full API sync runs.
 
### How it works — example
 
**Before backfill — `raw.workout_sessions`:**
 
| workout_session_id | started_at | hevy_workout_id |
|---|---|---|
| uuid-aaa | 2024-01-15 09:00:00 | NULL |
| uuid-bbb | 2024-01-17 18:00:00 | NULL |
 
**Hevy API returns:**
 
| hevy id | started_at |
|---|---|
| b459cba5 | 2024-01-15 09:00:00 |
| d812fce3 | 2024-01-17 18:00:00 |
 
**Backfill matches on `started_at` and updates:**
 
```sql
UPDATE raw.workout_sessions
SET hevy_workout_id = %s
WHERE started_at = %s
AND hevy_workout_id IS NULL
```
 
**After backfill:**
 
| workout_session_id | started_at | hevy_workout_id |
|---|---|---|
| uuid-aaa | 2024-01-15 09:00:00 | b459cba5 |
| uuid-bbb | 2024-01-17 18:00:00 | d812fce3 |
 
Now `ON CONFLICT (hevy_workout_id)` finds the existing rows and updates them
in place — no duplicates.
 
### Implementation
 
Create `utils/backfill_hevy_workout_ids.py` — a one-time standalone script,
not part of the regular sync pipeline.
 
**Logic:**
```
1. Fetch all workouts from GET /v1/workouts (full paginated fetch)
2. Build a dict: {started_at → hevy_workout_id}
3. Query raw.workout_sessions WHERE hevy_workout_id IS NULL
4. For each CSV row:
     match = api_dict.get(row["started_at"])
     if match found → UPDATE hevy_workout_id
     if no match found → log warning, skip
     if multiple CSV rows share same started_at → log ambiguity warning, skip both
5. Log total matched, skipped, ambiguous
```
 
### Risk: timestamp collisions
 
If two workouts share the exact same `started_at`, the match is ambiguous.
The script must detect this and skip both rather than guess. Log these cases
clearly so they can be resolved manually.
 
### Order of operations
 
```
1. Run backfill script once → confirm all CSV rows have hevy_workout_id populated
2. Verify no NULL hevy_workout_id remains in raw.workout_sessions
3. Only then run sync-hevy --mode full
```
 
**Never run the full API sync before the backfill completes.**
